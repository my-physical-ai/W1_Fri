PyTorch 내부 구조

PyTorch 내부 3대 핵심 기능 — LSE가 관여하는 곳

PyTorch가 import 단계에서 Pi 4에서 충돌하는 이유는 내부 3곳에서 LSE 명령어를 사용하기 때문입니다. 각각을 쉽게 설명합니다.

① 텐서 참조 카운팅 (Reference Counting)

📚
도서관 대여 카운터 비유

도서관에 책이 1권 있고 여러 학생이 같은 책을 공유합니다. 카운터에 "지금 몇 명이 이 책을 보고 있나?"를 기록하죠.
철수가 책을 펼침 → 카운터: 1 / 영희도 봄 → 카운터: 2 / 민수도 봄 → 카운터: 3
셋 다 다 보면 → 카운터: 0 → "이제 책 반납 (메모리 해제)"

💡 실제로는 — Python의 모든 객체(텐서, 리스트 등)는 "몇 개의 변수가 나를 가리키고 있나?"를 카운터로 관리합니다. 카운터가 0이 되면 메모리를 자동 해제합니다.

# 참조 카운팅 실제 동작 a = torch.tensor([1.0, 2.0]) # 메모리 생성, 카운터: 1 b = a # 같은 메모리 공유, 카운터: 2 c = a[:1] # 일부 공유, 카운터: 3 del b # 카운터: 2 del c # 카운터: 1 del a # 카운터: 0 → 메모리 자동 해제!
LSE 연결 포인트

카운터를 여러 CPU 코어가 동시에 수정하면 값이 틀려집니다. 코어A와 코어B가 동시에 카운터를 읽으면 둘 다 "2"를 읽고, 각자 "3"으로 쓰면 실제값은 4가 되어야 하는데 3이 됩니다. LSE의 ldaddal 명령어가 읽기+더하기+저장을 한 번에 처리해서 이를 방지합니다.

② 스레드 풀 작업 큐 (Thread Pool)

🏭
공장 작업 배분 비유

공장장(PyTorch)이 칠판에 할 일 목록을 씁니다. 일꾼 4명(CPU 코어)이 동시에 달려와 "나 이 일 할게!"라고 가져갑니다.
문제: 4명이 동시에 "1번 작업!"을 외치면? → 중복! 같은 작업을 두 코어가 함
해결: LSE로 "가져가기"를 원자적으로 처리 → 한 코어만 성공, 나머지는 다음 작업

💡 실제로는 — CPU 여러 코어에 행렬 연산을 나눠줄 때 작업 큐를 사용합니다. torch.mm(A, B) 하나가 내부적으로 코어 수만큼 작업을 분할합니다.

# 이 코드 한 줄이 내부에서는: C = torch.mm(A, B) # A×B 행렬 곱셈 # PyTorch 스레드 풀이 처리하는 과정: # 작업 큐: [행0~249] [행250~499] [행500~749] [행750~999] # # 코어1 ─── ldaddal로 [행0~249] 꺼냄 (잠금) ───→ 계산 # 코어2 ─── ldaddal로 [행250~499] 꺼냄 (잠금) ──→ 계산 (동시!) # 코어3 ─── ldaddal로 [행500~749] 꺼냄 (잠금) ──→ 계산 (동시!) # 코어4 ─── ldaddal로 [행750~999] 꺼냄 (잠금) ──→ 계산 (동시!) # # Pi 4 → ldaddal 없음 → 충돌 → Illegal instruction! # Pi 5 → ldaddal 있음 → 안전한 분배 → 정상 계산!

③ ARM Compute Library — 행렬 계산의 핵심 엔진

📐
구구단 비유

3×4를 계산할 때 3+3+3+3=12로 하면 느립니다. 구구단을 외우면 바로 "12"가 나오죠. ARM Compute Library는 행렬 곱셈의 "구구단책"입니다. 수백만 번의 연산을 최적화된 방법으로 처리하며, 내부 최적화 코드에 LSE 명령어가 직접 컴파일되어 있습니다.

💡 실제로는 — libarm_compute-84b761c0.so 파일 안에 ldaddal 명령어가 직접 포함됩니다. import 시 이 파일을 로드하는 순간 Pi 4에서 "Illegal instruction" 신호가 발생합니다.

AI가 로봇 팔을 제어할 때 1초에 수천만 번의 행렬 계산이 필요합니다. ARM Compute Library 없이는 실시간 제어가 불가능합니다.

PyTorch 탄생 이유와 독립적인 이유

탄생 배경: 연구자들의 불만에서 시작

😤
2016년의 불만

당시 지배자 TensorFlow(Google)의 문제:
"정적 그래프"를 먼저 설계한 후 실행 → 실험하기가 너무 불편
"AI 논문 새 아이디어 → 코드 구현 → 실행 → 오류 → 어디가 틀렸지?" 추적이 너무 어려움

연구자들의 요구: "그냥 Python처럼 줄 단위로 실행하면서 바로 확인하고 싶어!"

💡 비유 — TensorFlow는 "공장 전체 설계도를 다 그린 후 공장 가동". PyTorch는 "부품 하나씩 만들어가면서 바로 테스트". 연구자에게는 후자가 훨씬 편합니다.

PyTorch 2.10 주요 기능

Python 코드를 자동으로 최적화된 기계어로 변환합니다. Python 3.14의 GIL 없는 빌드(3.14t)와 결합하면 CPU 코어 전체를 진정으로 활용할 수 있습니다.

# 기존: Python 코드 그대로 실행 (느림) def my_model(x): return x * 2 + 1 # torch.compile 적용: 자동 최적화 (빠름) optimized = torch.compile(my_model) result = optimized(tensor) # 내부적으로 최적화된 코드 실행

분산 강화학습(RL) 등 복잡한 AI 훈련에서 "왜 갑자기 결과가 이상해졌지?"를 추적하는 도구입니다. LeRobot의 ACT 정책 학습 디버깅에도 유용합니다.

길이가 다른 여러 문장을 동시에 처리하는 새 연산자입니다. 로봇이 자연어 명령("빨간 컵을 왼쪽으로 옮겨")을 처리하는 VLA 모델 학습 효율을 높입니다.

GIL — 탄생, 한계, 제거까지 30년

🎤
발언권 막대기 비유

도서관 토론 규칙: 말하려면 반드시 "막대기"를 들어야 함. 막대기는 단 1개.
학생 8명이 있어도 막대기 든 학생만 말할 수 있고 나머지 7명은 기다려야 함.
→ GIL = Python의 단 1개짜리 발언권 막대기

💡 기술적으로는 — 모든 Python 코드를 실행하기 전 반드시 획득해야 하는 전역 잠금장치. 한 번에 1개 스레드만 Python 코드를 실행할 수 있습니다.

GIL이 왜 만들어졌나? (1991년)

# GIL이 없다면 이런 일이 생김: # 카운터 현재값: 5 # # 스레드A (코어1): 읽기 → 5 # 스레드B (코어2): 읽기 → 5 ← 동시에! # # 스레드A: 5 + 1 = 6 저장 # 스레드B: 5 + 1 = 6 저장 ← 덮어씀! # # 결과: 6 (실제로는 7이 되어야 함!) # → 메모리 오염 → 프로그램 오동작 또는 충돌 # GIL의 해결책: "동시 실행 자체를 금지" # 스레드A 완전히 끝날 때까지 스레드B는 대기 # → 충돌 원천 차단 (단, 코어 8개여도 1개처럼 동작)

GIL 제거가 왜 30년이나 걸렸나?

🏗️
30년된 건물의 내력벽 비유

GIL은 30년된 건물의 내력벽(건물 전체 무게를 지탱하는 핵심 벽)과 같습니다. 그냥 허물면 건물 전체 붕괴!

올바른 방법: ① 건물 전체 구조 파악 (수년 소요) → ② 내력벽 대신 다른 지지 구조 설계 → ③ 조금씩 교체하면서 테스트 → ④ 최종 검증 후 내력벽 제거

💡 GIL에 의존하는 것들: 참조 카운팅, 가비지 컬렉터, C 확장 모듈 수천 개(NumPy, pandas, OpenCV 등), Python 표준 라이브러리 전체. 이 모두를 GIL 없이도 안전하게 작동하도록 재설계해야 했습니다.

기술 비교

GIL vs CUDA — 같은 듯 다른 두 기술

💡
핵심: GIL은 CPU에서 Python 코드의 문제, CUDA는 GPU에서 수학 연산을 빠르게 하는 것. 완전히 다른 층위의 기술입니다.
🏭
AI 학습 공장 비유

공장장(Python, CPU): "데이터 불러와! 전처리해! GPU에 보내! 결과 받아! 저장해!"
→ GIL 문제 영역: 공장장 보조원들(스레드)이 동시에 일을 못함

공장 생산라인(GPU, CUDA): 1만 개 라인이 동시에 행렬 곱셈!
→ GIL과 완전히 무관. Python이 "시작!" 명령만 내리면 GPU가 알아서 처리

항목 GIL CUDA
위치CPU (Python 코드 실행)GPU (수학 연산)
목적Python 메모리 안전 관리대규모 병렬 수학 계산
만든 곳Python 언어 설계팀NVIDIA
문제CPU 코어 여러 개 못 씀없음 (병렬 처리 그 자체)
AI에서 역할데이터 준비, 제어 흐름행렬 곱셈, 학습 연산
Pi 5 관련GIL 제거 = LSE 덕분에 가능GPU 없어서 CUDA 불가
Pi 5에서 사용 가능?가능 (3.14t에서)불가 (NVIDIA GPU 없음)
# AI 학습 코드에서 두 영역이 어떻게 나뉘나: # ── Python(CPU) 영역 ── GIL 영향받음 ── 데이터 = 불러오기("dataset/") # GIL 영향 전처리 = 이미지_변환(데이터) # GIL 영향 배치 = 다음배치(전처리) # GIL 영향 # ── GPU 영역 ── CUDA ── GIL 무관 ── 배치_gpu = 배치.to("cuda") # GPU로 전송 출력 = 모델(배치_gpu) # CUDA 처리 (수천 코어!) 손실 = loss_fn(출력, 정답) # CUDA 처리 손실.backward() # CUDA 처리 (역전파) # ── 다시 Python(CPU) 영역 ── print(f"손실: {손실.item()}") # GIL 영향

Pi 5에서 GIL 제거의 실질적 의미

# 현재 (GIL 있음, Pi 5): ① 카메라 프레임 읽기 ────────────────┐ ② 이미지 전처리 (CPU) ────────────────┤ 순서대로 처리 ③ AI 추론 (PyTorch) ────────────────┤ (GIL 때문에) ④ 모터 명령 전송 ────────────────┘ # → 전체 약 100ms 지연 # Python 3.14t + GIL 제거 후 (Pi 5): ① 카메라 프레임 읽기 ── 코어1 ② 이미지 전처리 ── 코어2 ← 동시! ③ AI 추론 ── 코어3 ← 동시! ④ 모터 명령 전송 ── 코어4 ← 동시! # → 전체 약 30~40ms → 로봇 반응 2~3배 향상!

핵심 연결고리

GIL과 LSE의 연결 — 같은 문제의 두 해결책

🔑
핵심 한 줄: GIL = "LSE가 없던 시절의 소프트웨어 임시방편" / LSE = "GIL이 필요 없도록 하드웨어가 직접 해결한 것" → GIL과 LSE는 같은 문제(참조 카운팅 경쟁 조건)의 두 가지 해결책입니다.

공통 뿌리: 참조 카운팅 경쟁 조건(Race Condition)

# 두 기술이 해결하려는 같은 문제: 카운터 현재값: 5 코어A: 카운터 읽음 → 5 코어B: 카운터 읽음 → 5 ← 동시에! 코어A: 5 + 1 = 6 저장 코어B: 5 + 1 = 6 저장 ← 코어A 작업 덮어씀! 결과: 6 (7이 되어야 함!) → 메모리 오염 위험 # 해결책 1: GIL (소프트웨어, 1991년) "동시 실행 자체를 금지 → 코어A 끝날 때까지 코어B 대기" 결과: 정확 비용: 코어 8개여도 1개처럼 동작 # 해결책 2: LSE (하드웨어, 2016년) "ldaddal: 읽기+더하기+저장을 1개 명령어로 원자적 처리" 결과: 정확 비용: 없음! 기다림 없이 동시 진행

CPU 코어 1개, 원자 명령어 없음. GIL로 참조 카운팅 보호. 당시로선 최선의 선택.

소프트웨어만으로 GIL 없이 참조 카운팅을 안전하게 하려 하니 항상 성능이 나빠졌음.

하드웨어 수준에서 원자 연산이 가능해짐. 소프트웨어 루프 없이도 안전한 동시 카운터 수정 가능.
21
2021년 — Sam Gross: "LSE 같은 원자 명령어 쓰면 된다!"
"Biased Reference Counting": 주인 스레드는 잠금 없이 빠르게, 다른 스레드는 원자 명령어 사용. LSE가 있는 ARM에서 최고 효율.
25
2025년 — Python 3.14t: GIL 제거 공식화
LSE가 있는 Pi 5에서 최고 성능. Pi 4는 LSE 없어서 GIL 제거 시 오히려 느려질 수 있음.

Pi 4 vs Pi 5: GIL 제거에서도 차이가 나는 이유

상황 Pi 4 (LSE 없음) Pi 5 (LSE 있음)
참조 카운팅 ldxr + stxr 루프 반복 (실패 시 재시도) ldaddal 단 1번으로 완결
GIL 제거 후 참조 카운팅 오버헤드 폭증 → 느려짐 오버헤드 없음 → 빨라짐
PyTorch import Illegal instruction (LSE 명령어 없음) 정상 동작
Python 3.14t 사용 비효율 (LSE 없어서) 최고 효율 (LSE 완전 활용)

🎯 전체 핵심 5줄 요약

① LSE는 여러 CPU 코어가 메모리를 동시에 안전하게 수정하는 하드웨어 명령어 (ARMv8.1, 2016년)

③ PyTorch 2.4+는 LSE를 직접 사용하도록 설계되어 LSE 없는 Pi 4에서 import 단계부터 충돌
④ GIL 제거는 LSE 덕분에 가능해졌고, Pi 5에서 Python 3.14t + PyTorch 2.10 조합이 최고 효율
⑤ CUDA는 GIL/LSE와 전혀 다른 영역 — GPU 수천 코어로 행렬 계산을 병렬화하는 기술
